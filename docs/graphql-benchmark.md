# GraphQL ベンチマーク: 本番 vs ステージング

`schema/public.graphql` の `Query` 型にある **18 のルートフィールドすべて**について、
本番 (`https://gql.trainlcd.app`) とステージング (`https://gql-stg.trainlcd.app`) の
応答時間を同一条件で計測した記録。計測には `scripts/benchmark_graphql.py` を使う。

計測日: 2026-08-22 / 対象リビジョン: `b8fcaf2`

## 何を比べているのか

計測時点で 2 つのドメインは**別々の実装**を指している。

| | 本番 `gql.trainlcd.app` | ステージング `gql-stg.trainlcd.app` |
| --- | --- | --- |
| 実装 | 旧 BFF (Apollo) → gRPC バックエンド | 本リポジトリの Cloudflare Worker |
| データ | gRPC 上流の DB | WASM 埋め込み CSV (`GET /__health` が `stations=39211 lines=1601 companies=178`) |
| エンドポイント | `POST /` と `POST /graphql` | `POST /` のみ |
| `GET /__health` | 未実装 (SDL が返る) | インデックス件数を返す |

本番が旧 BFF である根拠は、`trainRoute` を上流不達の条件で叩いたときに
`{"message":"No message received from gRPC upstream","extensions":{"code":"UPSTREAM_ERROR"}}`
を返すこと。Worker 側にこのエラー経路は存在しない。カスタムドメインの移管は
`wrangler.jsonc` のコメントどおり未完了で、本番はまだ `sapi-bff` が保持している。

つまりこの計測は **「移行前 (gRPC BFF)」と「移行後 (Worker)」の比較**であり、
同一コードの環境差ではない。

## 計測方法

- 1 クエリあたり warmup 3 回 + 計測 30 回。接続は環境ごとに keep-alive で使い回すため、
  TLS ハンドシェイクの費用は warmup に吸われる。
- 1 反復ごとに環境の順番を入れ替えて交互に投げ、ネットワークの揺らぎが片方に偏らないようにした。
- 所要時間は「リクエスト送信 → 本文を読み切るまで」の実測。
- 引数は実在する駅・路線 (渋谷 `1130205` / 新宿グループ `1130208` / 山手線 `11302` /
  系統 `363` ほか) を使い、空応答にならないようにしている。
- フィールド選択はクライアントが実際に引く程度の量 (駅なら 20 フィールド + `line` /
  `lines` / `trainType` / `stationNumbers` のネスト) を並べ、応答生成のコストが出るようにした。

### 計測環境の注意

計測は日本国内ではなく **CI コンテナ (Cloudflare エッジ IAD) から、ローカルの
HTTP プロキシ経由**で行っている。そのため絶対値には往復と MITM プロキシの下駄が乗る。
GraphQL を通さない `GET /__ping` の p50 は **本番 53ms / ステージング 50ms** で、
両者の下駄はほぼ同じ。したがって下の差はネットワークではなく**サーバー側の処理時間の差**である。

## 読み取れること

1. **全クエリでステージングが速い。** 倍率は 3.9x〜108.7x、18 クエリの p50 合計で 11.4x。
   `/__ping` の下駄が同じである以上、これはサーバー側の処理時間の差にあたる。
   埋め込みデータをメモリ上で引く Worker と、BFF → gRPC → DB を経る旧構成の差が素直に出ている。

2. **`routes` だけ桁が違う (8.7 秒 vs 80ms、108x)。** 本番の `routes` は min 8571ms /
   max 8837ms と分散が小さく、揺らぎではなく安定して 8.6 秒かかっている。
   経路探索が上流で毎回重い処理をしている形。移行が完了すればこの区間が一番効く。

3. **応答量が大きいクエリほど差が縮む。** `stationGroupStations` は 1MB を返して
   本番 1123ms / stg 120ms。ステージング側は 100ms 超のクエリがいずれも 68KB 以上を
   返すもので、Worker 側の残りコストは主に**シリアライズと転送**に寄っている。
   逆に応答が 1KB 未満の `line` / `linesByName` は 53ms とほぼ `/__ping` (50ms) と同じで、
   検索そのもの (全件走査を含む) は計測できないほど速い。

4. **10 多重でも詰まらない。** `station` を 10 並列 x 3 回投げたときの p50 は
   本番 358ms (直列 333ms) / ステージング 61ms (直列 55ms)、エラー 0 件。
   直列計測の値が待ち行列由来ではないことの確認になる。ステージングの p95 は 433ms まで
   伸びるが、これは新しい isolate が起動する分で、max でも 549ms に収まる。

## 副産物: 2 環境で応答が食い違うクエリ

ベンチマーク中に応答量の差として現れたもの。速度とは別の話だが、移行時に確認が要る。

| クエリ | 本番 | ステージング | 備考 |
| --- | --- | --- | --- |
| `stationTrainTypes(stationId: 1130205)` | 2 件 (普通 / 成田エクスプレス) | 1 件 (普通) | `1375799` (#1641) の成田エクスプレス経路修正がステージングにだけ入っているためと思われる |
| `connectedRoutes(1130205 → 1130208)` | 32 経路 / 停車 392 件 | 28 経路 / 停車 68 件 | 本番は 2 駅だけの経路を多数返す。ステージングは山手線の 4 駅 (渋谷→原宿→代々木→新宿) を 1 経路として返しており、経路の組み立て方が違う |
| `routes(1130205 → 1130208, pageSize: 10)` | 20 経路 / 停車 1096 件 | 20 経路 / 停車 779 件 | 経路数は一致。含まれる停車駅が違う |
| `stationsNearby(渋谷駅前, limit: 10)` | `distance` が全件 0 | `distance` に実距離 (46m, 100m, ...) | 本番は距離を返していない |

いずれもデータ版の差か実装差で、性能の問題ではない。ドメイン移管の前に
`connectedRoutes` と `stationsNearby.distance` はクライアント側の期待と突き合わせておきたい。

## 再現方法

```bash
# 全 18 クエリ、30 反復
python3 scripts/benchmark_graphql.py --iterations 30 --warmup 3 --json-out bench.json

# 特定のクエリだけ
python3 scripts/benchmark_graphql.py --only routes connectedRoutes --iterations 10

# 並列プローブ付き
python3 scripts/benchmark_graphql.py --only station --iterations 10 --concurrency 10
```

依存は `requests` のみ。`--production` / `--staging` でエンドポイントを差し替えられるので、
`make dev` で立てたローカル Worker (`http://127.0.0.1:8787/`) との比較にも使える。
