## 所見

### 本番とステージングに実装差は無い

`origin/master..origin/dev` は `bf6f92d`「バージョン管理手順を jj から git へ戻す」1 コミットだけで、
中身は `AGENTS.md` と `.claude/skills/` のドキュメントのみ。**Rust のコードは 1 行も違わない。**
上の表で `stationsNearby_limit100` / `lineGroupStations` / `lineListStations` /
`lineGroupListStations` が「stg 速い」に振れているが、これは実装差ではあり得ない。
追試で本番の `__ping` が 26.3 ms → 47.6 ms と実行ごとに倍近く動いたので、
サーバ分の補正が吸収しきれなかった回線由来の揺れとみる。
**次のリリースで本番の性能が変わる要素は無い。**

なお `/__health` は本番 39217 駅 / ステージング 39226 駅で 9 駅ずれていた (0.02%)。
性能比較を歪める量ではないが、完全一致という前提は崩れている。

### 応答時間はほぼ全部ペイロード量で決まっている

本番のサーバ分をレスポンスサイズで割ると、ほとんどのケースが 0.07〜0.10 ms/KiB に収まる
(`station` 0.135、`stationsByName` 0.139、`connectedRoutes` 0.177、`routeTypes` 0.83 が外れ値)。
索引引きの重さではなく、**組み立てとシリアライズの量が支配項**ということ。

射影だけを落とした追試 (本番のサーバ分):

| クエリ | 全フィールド | 最小射影 (`id` のみ) | `lines`/`line`/`trainType` を外す |
| --- | ---: | ---: | ---: |
| `lineListStations` | 1012.5 KiB / 75.9 ms | 8.8 KiB / 37.9 ms | 109.0 KiB / 38.8 ms |
| `stationGroupStations` | 1336.1 KiB / 71.5 ms | 3.4 KiB / 23.2 ms | — |
| `routes` | 901.2 KiB / 64.4 ms | 15.9 KiB / 29.0 ms | — |
| `stationsNearby(limit:100)` | 615.9 KiB / 38.1 ms | 1.5 KiB / 17.2 ms | — |

読み方は 2 つ。

1. **ペイロードの 89% は `lines` が作っている。** `lineListStations` で `lines`/`line`/`trainType`
   を外すと 1012.5 KiB → 109.0 KiB、サーバ分も 75.9 ms → 38.8 ms に落ちる。
   `update_station_vec_with_attributes` は駅ごとに所属路線を `clone()` で詰め、
   さらに `line.station = Some(station.clone())` で駅を埋め戻すので、駅数 × 路線数で膨らむ。
2. **射影を捨てても半分は残る。** `id` だけ要求した `LL_min` でも 37.9 ms 掛かっている。
   付帯情報の組み立ては use case 層で GraphQL の選択セットと無関係に走るため、
   クライアントが `lines` を要求していなくても全部組み立ててから捨てている。

### 打てる手

- **クライアント側で今日から効く。** `lines` を使わない画面では要求しない。
  地図の近傍表示のようにバス路線が不要な場面では `transportType: Rail` を渡す。
  サーバの変更を待たずに 4〜6 割落ちる。
- **サーバ側は選択セットを見て組み立てを省くのが筋。** `async-graphql` の
  `ctx.look_ahead()` で `lines` が要求されているかを見て、不要なら
  `update_station_vec_with_attributes` のバス探索と路線 `clone()` を丸ごと飛ばす。
  `LL_min` の 37.9 ms のうち相当分がここで消える。
- **近傍バス路線を `lines` に混ぜている設計自体を見直す余地がある。**
  「この駅が属する路線」と「この駅の近くを通るバス路線」は意味が違うのに同じ配列に入っており、
  クライアントは片方だけを選べない。専用フィールドへ分ければ、既定の応答が半分になる。
- **CPU Time を取り直す。** 今回は `wrangler` の認証が無く欠測で、判定を応答時間だけで
  行っている。`workers_tail (read)` のある環境で回せば、上の切り分けを
  ネットワーク抜きで確認できる。


## 測り方の限界

- `wrangler tail` の `cpuTime` はミリ秒の整数なので、1〜2 ms のクエリは丸めの影響が大きい。平均は反復数ぶん細かくなるが、1 反復の値は信用しない。両環境とも平均 1 ms 未満のケースは判定を「分解能未満」として保留している。
- 本番とステージングは別の Worker であり、暖まり具合もリクエストの割り当て先マシンも独立している。コールドスタートの有無で 100 倍単位の差が出るため、判定は定常標本だけで行っている。コールドかどうかは固定閾値ではなく、同じケース内の中央値からの跳ね方で決めている(もともと数百 ms 使うクエリを巻き込まないため)。
- 応答時間には計測ホストから Cloudflare エッジまでの回線が乗る。本番とステージングのどちらを先に叩くかは 1 リクエストごとに入れ替えており、回線の変動が片方へ偏らないようにしてある。
- 標本は「全ケースを 1 巡」を反復数ぶん繰り返して集めており、各ケースの標本は実行時間全体へばらしてある。それでも実行をまたぐと平均は動く(実測で、同じクエリのステージング平均が別実行で 89 ms と 52 ms に割れたことがある)。**2 倍に満たない差は、もう一度まわして同じ向きに出るまで結論にしない。**
- データは両環境で同一 (`/__health` で確認できる)。差が出たら実装差とみなしてよい。
